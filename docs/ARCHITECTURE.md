# Архитектура и выбор подхода

## Решение

Один LLM-планировщик предлагает проверяемые конфигурации; собственный ML-движок
обучает модели в ограниченных процессах. Внешний интерфейс —
`python3 solution.py task.md`, выход — `submission.csv` рядом с задачей.

| Подход | Качество | Надёжность и ресурсы | Решение |
|---|---|---|---|
| Готовый AutoML | Потенциально сильные ансамбли | Требуется согласовать внутренний поиск, валидацию и резерв refit с агентом | Не включён в основной стек |
| Свободный LLM-агент с выполнением кода | Гибкость на новых постановках | Ошибки программ, непредсказуемые затраты и сложная изоляция | Не выбран |
| Qwen + линейные модели, бустинги, лес и допустимая история | Проверяемые гипотезы, разные ошибки моделей | Явные бюджеты, воспроизводимые конфигурации, аварийный режим | Реализован в v4 |

Сравнение подходов — инженерное решение, не результат сравнительного обучения
всех AutoML-фреймворков. Качество конкретных моделей проверяется экспериментами.

## Разделение ответственности

- `task_reader.py`, `data_io.py`: контракт и профиль материалов без изменения данных.
- `validation.py`: поисковая и подтверждающая части, время и группы.
- `preprocessing.py`, `models.py`, `metrics.py`: обучаемые преобразования, модели, оценка.
- `novel_models.py`, `novel_worker.py`: ограниченный ExtraTrees в штатном портфеле;
  ядро и метрическая память в отдельном исследовании.
- `research.py`, `llm_client.py`: следующий эксперимент, проверка гипотез и лимиты API.
- `sgr_planner.py`: необязательный планировщик со строгой схемой через `--planner sgr`.
- `history_router.py`, `historical_features.py`: история прошлых периодов при
  подтверждённом ключе сущности; резерв для неизвестных сущностей.
- `oof_ensemble.py`: фолды внутри search-train, прогнозы трёх семейств и веса смеси.
- `runtime.py`, `worker.py`: генерация программы, процессы, мягкие и жёсткие остановки.
- `submission.py`: формат, идентификаторы и атомарная запись.
- `submission_audit.py`: проверка сериализованного CSV и безопасный манифест.
- `experiment_store.py`, `solution.py`: журнал, выбор финалистов и завершение.

## Независимость валидации

При наличии будущего периода теста используется временная схема. Если доступны
хотя бы четыре периода обучения, предыдущий период служит для поиска, последний —
для подтверждения. Для обычных задач резервируются отдельные части поиска и
подтверждения. При повторах одинаковые признаки не пересекают границы групп.

Преобразования и частоты категорий обучаются только на train-части эксперимента.
LLM не может менять метрику, разбиение и источник данных. Вес ансамбля выбирается
на search, затем проверяется неизменным на confirm. Оценка на confirm используется
для ограниченного выбора финалиста, а не для продолжения поиска.

Лидер и до двух дополняющих семейств отбираются по поисковой метрике смеси.
Это сохраняет модель, полезную совместно с лидером, даже если её самостоятельное
качество ниже. Конфигурации, веса и число итераций записываются в `finalists.json`
до подтверждения; ранней остановки на подтверждении нет. Выбор между уже
зафиксированными подтверждёнными кандидатами не является новым слепым тестом.

## Обязательная линейная модель и OOF в v4

Первый эксперимент — Ridge для регрессии или логистическая регрессия для
классификации, в том числе на числовых данных без текста. Прежние существенные
контроли остаются обязательными перед остановкой из-за отсутствия прогресса.

OOF выбирает лучшего представителя бустинга, ExtraTrees и linear по поиску.
Каждый обучается заново на одинаковых внутренних фолдах search-train со своим
профилем и преобразованиями. Количество итераций фиксировано; OOF-valid не
используется для ранней остановки. Повторы разделяются группами, время —
расширяющимся прошлым с непроверяемым начальным периодом.

Веса подбираются на сетке из 73 вариантов; нулевые веса допустимы. После
фиксации они проверяются на отдельной search-valid. До confirm сохраняются
прежний план, контроль и принятый поиском OOF-план. На confirm сначала
применяется прежнее правило выбора между планом и контролем, затем OOF
сравнивается с его результатом. Неполная OOF-проверка не вытесняет прежний план.

OOF использует до 12% общего лимита и заканчивается не позже границы 70%
времени задачи. При недостатке времени, памяти или независимых фолдов этап
пропускается; ошибка фолда отменяет всю новую смесь. `--no-oof` отключает этап.
[Результаты и ограничения](LINEAR_OOF_RESEARCH.md).

## Генерация программ

LLM возвращает JSON языка конфигураций. Разрешены три семейства моделей и
небольшой набор операций над подтверждёнными признаками. Неизвестные поля,
нечисловые параметры, выходы за диапазоны и обращения к таргету отклоняются.
Контроллер генерирует `experiment.py` из фиксированного шаблона. Произвольные
команды, импорты и строки кода из ответа LLM не исполняются.

Это генерация программы по управляемому описанию. В материалах не уточняется,
обязаны ли команды поддерживать свободную генерацию произвольного Python;
формальный критерий следует подтвердить у организаторов.

## Бюджеты

Поиск получает до 70% общего времени, подтверждение — до 84%, refit — до 97%.
Это верхние границы, не обязательные задержки. У процесса обучения есть мягкий
предел, сохраняющий модель, затем внешний watchdog времени и памяти. Незавершённый
refit не заменяет проверенные предсказания. Общий таймер ограничивает также
профилирование и запросы API. Финальный CSV заменяется только после проверки.

Лимит памяти учитывает родительский процесс и доступный cgroup/хостовый резерв.
Ключ LLM остаётся у контроллера. Вычислительные процессы получают только
ограниченный набор переменных окружения.

## Границы поддержки

Поддерживаются однотаргетные табличные задачи с известными метриками и CSV.
Для текстовых столбцов есть TF-IDF, но это не универсальный NLP-агент.
Нет заявленной поддержки изображений, ранжирования и произвольных новых метрик.
Неизвестная метрика сначала уточняется через LLM из реестра; неподдерживаемая
формула не исполняется. При недостатке информации сохраняется аварийный ответ
в подтверждённой выходной схеме.
