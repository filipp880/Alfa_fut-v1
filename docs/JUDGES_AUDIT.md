# Аудит после замечаний судей

26 октября 2026 года. Основание проверки — [зафиксированный протокол](JUDGES_AUDIT_PROTOCOL.md).

Подтверждены и исправлены воспроизводимые дефекты обработки имён признаков LightGBM, положительного класса `0.0` и некорректных входов LLM-клиента. Добавлена безопасная диагностика. Модельные гиперпараметры и правила выбора ансамбля сохранены. Подготовлен отдельный ZIP-кандидат; его полные локальные прогоны на момент составления документа ещё выполняются.

Со слов пользователя, v2 получил **21,86 балла и место 110 из 220**; лидер — 30, граница топ-10 — 27,58. Судьи сообщили о корректном завершении обеих задач и предложили проверить конфигурацию LLM-клиента и возможную ошибку LightGBM в одном эксперименте. Полного судейского traceback и снимка окружения нет. Найденные локальные дефекты пока нельзя объявить причиной предупреждения или балла. Платформенные баллы также нельзя напрямую сопоставлять с локальными RMSE и Macro F1 без правил платформенной оценки и скрытых разбиений.

## Как работает агент

1. `solution.py` читает условие, словарь и таблицы, определяет контракт таргета и ответа. После разрешения метрики сохраняет резервный `submission.csv`. Это позволяет оставить проверенный ответ при последующих сбоях поиска или refit.
2. Выбираются фиксированные search и confirm. При временной оси обучение предшествует проверяемому периоду; для повторяющихся одинаковых X применяются групповые разбиения. Профиль для поиска строится по search-train.
3. `Research` выдаёт локальные рецепты CatBoost, LightGBM и других разрешённых моделей. На **каждом третьем шаге выбора эксперимента**, начиная с третьего, он может запросить предложение LLM, если доступны ключ, вызовы, токены и время. Это возможность вызова, а не обязательный запрос: при отказе, неверном или повторном предложении продолжается локальная очередь.
4. LLM получает условие, разрешённые признаки и классы, профиль и краткую историю собственных поисковых экспериментов. Он возвращает проверяемый JSON-конфиг закрытого DSL; произвольный исполняемый код не принимается. Подтверждающие оценки в поисковую историю не подаются.
5. Каждый ML-эксперимент работает в дочернем процессе с ограничениями времени и памяти. Ключ API не передаётся worker. Преобразования обучаются на его tr-строках; метрики вычисляются на исходной шкале таргета. Родитель проверяет порядок validation indices и воспроизводимость score.
6. Состав ансамбля, веса и числа итераций выбираются на search. Confirm проверяет замороженный план и допускает возврат к заранее выбранному контролю. Для полного refit используются фиксированные числа итераций. Новый полный ответ заменяет прежний только после успешного завершения всех выбранных компонентов.

Реализация: [solution.py](../solution.py), [research.py](../research.py), [runtime.py](../runtime.py), [contracts.py](../contracts.py).

### Бюджет и завершение

Все доли считаются от общего времени запуска, включая чтение данных, API и обучение:

| Граница | Назначение |
|---|---|
| 70% | Окончание поискового бюджета; LLM также ограничен этой границей. |
| 84% | Бюджет подтверждения заранее выбранных кандидатов. |
| 97% | Бюджет полного refit с оценкой необходимого резерва. |
| Общий deadline | Отдельный watchdog ограничивает весь процесс; штатный предел — 10 800 секунд. |

По умолчанию разрешены до 18 поисковых экспериментов и до 6 LLM-вызовов. Ранняя остановка поиска возможна. Настройка SDK timeout ограничена 35 секундами и остатком поискового времени, `max_retries=0`, `max_tokens=1000`, температура — 0,15. Для проверенного Qwen сохранены три флага отключения thinking и `/no_think` в пользовательском сообщении. Обычный планировщик остаётся основным; SGR включается явно.

Имена `OPENAI_API_KEY`, `OPENAI_BASE_URL` и `OPENAI_MODEL` сопоставлены с официальным `baseline.py` из материалов организаторов. Отсутствующий ключ выключает LLM-ветвь. Присутствие ключа, эффективные model/gateway, причины пропуска, стадия ошибки, HTTP status и finish reason теперь видны в безопасной диагностике. Credentials, query, ключи, заголовки и тела API-ошибок в неё не копируются.

## Проверка корректного завершения

Помимо тестов моделей выполнены отдельные проверки жизненного цикла с инъекцией отказов. Они не использовали API или ML fit и не меняли runtime. Общий результат — `passed: true` в [process_fault_checks.json](../runs/judges_audit/process_fault_checks.json).

| Проверка | Фактический результат |
|---|---|
| Общий deadline при зависшем профилировании | При лимите 10 секунд процесс завершился за 9,875 секунды с кодом 0 и статусом `deadline`. CSV сохранил 50 корректных строк; родительский процесс завершён. |
| Таймаут дочернего worker | При лимите 2,5 секунды остановка заняла 2,797 секунды. Worker и его потомок завершены; ключ API отсутствовал в окружении worker. |
| Исключение confirm | Код 0, `recovered_with_submission`, корректный CSV. SHA-256 до и после совпадает. |
| Неуспешный refit | Код 0, `completed`; прежний корректный CSV сохранён с тем же SHA-256. |
| Исключение refit | Код 0, `recovered_with_submission`; прежний корректный CSV сохранён с тем же SHA-256. |

Статус `completed` сам по себе не означает успешный полный refit: для этого отдельно проверяются `refit_completed`, источник прогнозов и CSV-манифест. В диагностике завершения теперь сохраняются также фактические счётчики LLM и идентификатор итогового CSV.

## Решение и выпуск

Включить воспроизведённые исправления и безопасную диагностику. Сохранить
модельные гиперпараметры и правила поиска: публичное качество не ухудшилось.
В проверенных сценариях fallback, global watchdog и сохранение CSV работают
корректно. Все 37 обучений двух полных задач успешны, оба refit завершены.
Подтверждённых дефектов завершения в этих сценариях не осталось.

Готовый [alfa_solution_v3_audit_2026-10-26.zip](../dist/alfa_solution_v3_audit_2026-10-26.zip)
побайтно равен проверенному кандидату: 71090 байт, SHA-256
`752afaae4fa813879bb301d7464924d9217a77999502ce10aa764ee36ed35483`.
V2 сохранён. Новая отправка на платформу автоматически не выполнялась.

Платформенные 21,86 балла принадлежат v2; результат v3 на платформе неизвестен.
Фраза судей не содержит traceback, эффективного model/base URL и HTTP-статуса.
Точную причину их предупреждения пока установить нельзя. Новая stdout-диагностика
различает missing key, HTTP401/404/400, timeout, пустой/обрезанный JSON и ошибку
ML без раскрытия ключа. Это подтверждённые исправления устойчивости и контракта,
без обещания определённого прироста баллов.
