# Воспроизведение экспериментов v4

Цель — отделить эффект обязательного linear от эффекта OOF. Сначала фиксируются
входы, ZIP, разбиения, лимиты и критерии выбора; confirm не используется для
продолжения поиска или изменения весов.
[Исходный протокол](LINEAR_OOF_PROTOCOL.md), [завершённое сравнение](LINEAR_OOF_RESEARCH.md).

## Варианты и материалы

| Вариант | Архив | Дополнительный аргумент |
|---|---|---|
| A: прежний портфель | `dist/alfa_solution_v3_audit_candidate.zip` | — |
| B: ранний linear | `dist/alfa_solution_v4_2026-10-27.zip` | `--no-oof` |
| C: ранний linear и OOF | `dist/alfa_solution_v4_2026-10-27.zip` | — |

Нужны Python 3.12, зависимости исследовательского стенда, работающий Docker и
заранее собранный образ `alfa-research:local`. Исходные организаторские данные
готовятся через `tools/prepare_public.py`; они не входят в Git. Образ собирается
до эксперимента, а не внутри запуска агента:

```bash
docker build -f Dockerfile.research -t alfa-research:local .
```

## Полный публичный прогон

Из корня проекта, пример для B:

```bash
python tools/run_release.py runs/public/regression/task.md --zip dist/alfa_solution_v4_2026-10-27.zip --cpus 4 --memory-gb 14 --max-experiments 18 --time-limit 10800 --no-oof
```

Для C уберите `--no-oof`; для A выберите старый архив и уберите этот флаг.
Для классификации замените путь задачи на `runs/public/classification/task.md`.
Число итераций в этом инструменте не ограничивается. Запуски выполняются без
LLM и сети. Каждый получает собственный каталог `runs/release/<case>`, только
свои входы и код; готовые модели или прогнозы других вариантов не передаются.

Одновременно запускайте не больше двух таких контейнеров: суммарно до
8 CPU / 28 ГиБ. Лимит 10800 с относится к каждой задаче целиком, включая
подготовку, поиск, OOF, confirm и refit. Время соседних запусков зависит от
нагрузки и само по себе не доказывает ускорение алгоритма.

## Синтетика и отдельный тест

```bash
python tools/make_linear_benchmarks.py
```

Генератор создаёт регрессию и трёхклассовую классификацию с фиксированными
seed 271026/271027: 1500 обучающих и 400 тестовых строк, 12 числовых признаков.
В регрессии тестовые признаки имеют увеличенный масштаб для проверки
экстраполяции. `oracle_test.npz` остаётся у внешнего проверяющего.

Запускайте A/B/C тем же `tools/run_release.py` с путями
`runs/linear_benchmarks/linear_regression/task.md` и
`runs/linear_benchmarks/linear_classification/task.md`, но с
`--max-experiments 6`. Инструмент копирует только пять входных файлов и ZIP,
поэтому oracle не попадает в ML-контейнер. Он используется только при
последующем независимом подсчёте тестовой метрики.

## Независимая проверка артефактов

Для своего завершённого каталога:

```bash
python tools/report_release.py runs/release/<case> --output runs/my_release_report.json
python tools/audit_oof_release.py runs/release/<case> --output runs/my_oof_report.json
```

Проверяются входные хэши и код ZIP, индексы и группы, хронология, метрики из
прогнозов, фиксированные итерации и состав плана до confirm, полный refit и
совпадение CSV с его прогнозами. Для OOF дополнительно реконструируется матрица
фолдов и пересчитываются все 73 набора весов. Для синтетики внешний reporter
вычисляет тестовую метрику по oracle; runtime агента его не читает.
Эти reporters предназначены для задач данного исследования с RMSE/Macro F1.

`tools/report_linear_oof.py` собирает исходную таблицу по сохранённым путям
завершённого исследования. Эти локальные `runs` не публикуются, поэтому в
свежем клоне используйте отдельные reporters для собственных новых каталогов.
`tools/audit_release_models.py --index <таблица.json> --output <аудит.json>`
дополняет проверку фактическими моделями. В таблице нужны поля `directory`
(путь относительно корня) и `arm`; записи A пропускаются. Загружать в этот
инструмент следует только собственные доверенные модели: он читает pickle/joblib.
